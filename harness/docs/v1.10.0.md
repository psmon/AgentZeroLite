# v1.10.0 — audio-regression-review engine (Music + Voice curator release lane)

**Released**: 2026-08-08
**Bump rationale**: Minor — new engine. Adds the 7th engine
(`audio-regression-review`) orchestrating the two audio-domain curators
(`music-curator` + `voice-curator`) as a release-time advisory review. No
existing agent, engine, or knowledge file is modified beyond the config
registration — pure addition.

## Why this change

The 2026-08-08 roster analysis (`harness/logs/tamer/2026-08-08-19-57-agents-roster-analysis.md`)
surfaced a gap: the harness has **two audio-domain curators** but no
release-time workflow that exercises them. Both `music-curator` and
`voice-curator` are *advisory consult* agents ("call me before you change
X") — and nothing calls them at release time.

The two existing safety lanes miss audio regressions entirely:

- `release-build-pipeline` gate = `security-guard → build-doctor` — it
  reviews injection surface and build integrity, not mel preprocessing or
  diarization pairing.
- The test lane (`test-runner` / `test-sentinel`) does **not** execute
  audio smoke tests by policy (LLM-smoke cost).

So a release that changes `MelSpectrogram.ComputeLogMel`, the WASAPI
`LoopbackCaptureService` sample-provider chain, the `SherpaSpeakerDiarizer`
segmentation+embedding pair, or the Whisper×Sherpa transcript-merge math
silently ships — degraded mAP / DER / capture-format correctness with no
exception thrown.

The just-shipped **v0.16.0** (voice-note diarization chunk-scoping +
agent-band loopback fix) is exactly this change class: it touched
`voice-curator` and `music-curator` watched paths and shipped without
either curator reviewing it. That release is the motivating example.

Per `harness/creator-rule.md` Rule 2, a review that needs 2+ agents to
coordinate is an engine — not something embedded in either curator's file
(Rule 1 forbids curators calling each other inline).

## What's new

### Engine: `audio-regression-review`

- File: `harness/engine/audio-regression-review.md`
- Agents: `[music-curator, voice-curator]` (run independently; engine
  aggregates)
- Triggers (en + ko): `"오디오 회귀 점검해"`, `"오디오 회귀 리뷰"`,
  `"audio regression review"`, `"audio regression check"`,
  `"음성 오디오 회귀 점검"`
- Auto-invoke (declared, wiring deferred): under `release-build-pipeline`
  when the release diff since the last `v*` tag touches an audio-watched
  path.

**Behavior:**

1. **Change-detection routing** — matches the diff against each curator's
   "Files this agent watches" list. No audio path touched → **no-op**
   (cheap exit, one-line log). This keeps non-audio releases free.
2. **Per-lane review** — music paths → `music-curator`; voice paths →
   `voice-curator`. Both may fire (shared `LoopbackCaptureService` ripples
   into Voice's reused capture path). Each writes its own log (Rule 6).
3. **Verdict** — advisory by default. A curator **Pass/Fail-axis Fail**
   (broken capture format, wrong diarization pair, non-16 kHz sample rate)
   escalates to **recommend-block**; A/B/C/D weakness stays advisory.
4. **Never a hard gate** — unlike `security-guard`, this engine informs
   the operator, who owns the release decision. Waivers follow the same
   protocol as `release-build-pipeline` (`## Waiver` section in the
   failing curator's log).

## Rollback procedure

If the engine proves redundant (e.g. audio work stabilises and manual
curator consults suffice):

1. Revert `harness/harness.config.json` to v1.9.0 (drop the engine entry,
   restore version + lastUpdated).
2. Delete `harness/engine/audio-regression-review.md`.
3. Add a v1.10.1 doc explaining the removal.

The curators (`music-curator`, `voice-curator`) are untouched by this
change, so rollback is limited to the engine + config.
