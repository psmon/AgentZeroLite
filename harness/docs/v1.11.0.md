# v1.11.0 — pr-review engine (branch-level verification lane)

**Released**: 2026-08-20
**Bump rationale**: Minor — new engine. Adds the 10th engine (`pr-review`)
orchestrating four existing agents (`code-coach` + `build-doctor` +
`test-runner` + `security-guard`) as a pull-request verification lane. No
existing agent, engine, or knowledge file is modified beyond the config
registration — pure addition.

## Why this change

The garden had a staged-diff reviewer (`pre-commit-review`) and a release
lane (`release-build-pipeline`), but nothing at **pull-request** scale. When
the operator asked for PR #12 to be verified — "단순히 코드리뷰가 아니라
유닛테스트 및 e2e테스트 진행, 작업 잘 되었나 검증" — the steps had to be
assembled by hand from three agents, which is exactly the re-derivation this
harness exists to eliminate.

The gap is not one of severity but of **evidence**. `pre-commit-review`
answers "is this diff sane?" from a diff read alone. A PR asks whether the
work actually landed, and that needs measurements a diff cannot supply:

1. **A build.** A diff that reads fine can still not compile.
2. **Both test suites.** `ZeroCommon.Tests` and `AgentTest` fail for
   different reasons; only the former runs unattended.
3. **A baseline on the merge target.** "483 tests pass" is meaningless
   without knowing what the target scores. On the run that produced this
   engine, the PR body claimed `baseline 473, +10`; the measured baseline
   was **478** and the delta **+5** — matching the same body's "5 tests
   added" line. Only a worktree run on `main` surfaced that.
4. **The e2e smoke.** Unit-green has never proven the app launches.
5. **Verification of the PR body's own claims** against what the commands
   printed.

None of the existing engines cover that combination:
- `pre-commit-review` — staged files, one reviewer, seconds. Correct for
  its scope, and deliberately not widened; a heavyweight pre-commit gate
  would be abandoned within a week.
- `release-build-pipeline` — fires *after* the merge decision, on a tag.
- `os-cli-e2e-smoke` — one gate, not a verdict-producing workflow.

## What the engine pins

Beyond the step sequence, three disciplines that were improvised on the
first run and are worth making binding:

- **Baseline via worktree, never `git checkout`.** Checking out the merge
  target mutates the branch under review and strands the operator if the
  run dies partway.
- **Blame the probe before the PR.** When the e2e smoke failed on the first
  run, hand-reproducing its steps showed the *product* was fine and the
  *script* was broken (issue #13). An engine that skips this attributes
  infrastructure rot to whoever happens to open the next PR.
- **In-scope vs out-of-scope, never mixed.** The operator reading a PR
  comment needs to know what blocks *this* merge. Out-of-scope findings go
  to issues, and the PR comment links them.

The engine is also explicitly **non-destructive**: it never runs `gh pr
merge`, `gh pr close`, or `gh pr review --approve`. Its output is a comment
and a set of issues. An advisory reviewer that can close PRs stops being
advisory.

## Known gate hazards table

`harness/engine/pr-review.md` carries a table of currently-broken gates with
their issue numbers (#13 e2e probe + element-tree hang, #14 `AgentTest`
under-reporting, #15 stale `NU1903` pin). This exists so the engine does not
attribute a known-broken gate to the PR under review. **It needs
maintenance** — as those issues close, the rows come out. A stale hazard
table would suppress real findings, which is the worse failure direction.
