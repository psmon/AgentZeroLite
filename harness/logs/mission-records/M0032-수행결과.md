# M0032 수행결과 — 웨어러블 호스트 AI 영역 강화

## 수행 요약

브리프의 두 기능(허용목록 기반 파일 검색·분석·열기, GUI 웹뷰 기반 웹 검색·탐색)을
운영자 추가 지침대로 **별도의 액터 모델**로 구현했다. 메인 앱의 `AgentLoopActor`를
그대로 재사용하고, 그 위에 웨어러블 전용 감독 액터(`WearableAgentActor`)와 파일·웹 툴
액터를 두었다. `ChatActor`는 워치 입출력만 남았다.

디스패치 순서: tamer → code-coach(구현) → security-guard(세 경계 점검, 1건 즉시 수정)
→ test-runner(headless + WPF 전체 테스트). 각 전문가 로그는 아래 "비고"에 링크.

## 결과

### 1) 액터 토폴로지 (호스트 ActorSystem `AskBot`)

```
/user/chat                 ChatActor            — 워치 I/O만 (BLE / AskBot / 음성)
/user/agent                WearableAgentActor   — 세션 관리, 라우팅, 최신 질문 우선
    /files                 FileToolActor        — 허용목록 해석 + read/grep/list + open_file
    /web                   WebToolActor         — GUI 브리지(-cli web) → 헤드리스 폴백
    /session-<key>         AgentLoopActor       — 메인 앱 액터 재사용, 대화당 1개
```

- `AgentLoopActor`는 수정 없이 재사용. 워치에 필요한 "새 질문이 이전 질문을 이긴다"
  규칙(실행 중 취소 + Idle 될 때까지 대기열)은 부모인 `WearableAgentActor`가 맡는다.
- 액터·툴벨트는 WinRT 의존이 없어 **ZeroCommon**에 두었고, 그래서 `ZeroCommon.Tests`의
  TestKit 테스트(`WearableAgentActorTests`, 9건)로 검증된다.
- `--ask` 스모크는 로컬 ActorSystem 위에서 같은 서브트리를 통과한다(패널 "Test brain").

### 2) 파일 허용목록 + open_file

- `wearable-settings.json`에 `AllowedRoots[{Alias, Path, Writable}]`. 기존 `WorkspaceRoot`는
  로드 시 alias `workspace`(writable)로 자동 이관·비움.
- 모델 경로는 `alias/relative/path`. `list_files`에 경로가 없으면 alias 목록만 돌려준다
  (실제 경로는 절대 노출되지 않음). 쓰기는 폴더별 `Writable`이 켜진 곳만.
- `open_file`: 확장자 **허용목록**(미디어/이미지/문서)만 ShellExecute. `.exe .lnk .ps1
  .bat .cmd .js .msi .html` 거부, `song.mp3.exe`도 거부(테스트).
- Wearable 패널에 허용 폴더 편집(추가/삭제/writable) + 웹 툴 토글. 저장 = 재시작 계약 유지.

### 3) 웹 툴 — GUI Browser 페이지 우선, 헤드리스 폴백

- 새 동사 `web_search` / `web_open` / `web_read`(+`open_file`)를 공유 카탈로그
  `AgentToolGrammar`에 추가(GBNF·KnownTools·프롬프트). 두 루프 모두 디스패치.
- GUI에 **Browser 페이지**(액티비티 바) 신설: 탭 열기/닫기/전환, 주소창(URL 또는 검색어),
  뒤로/새로고침. 워치 에이전트가 페이지를 열면 자동으로 이 페이지가 뜬다.
- 호스트 → GUI는 기존 `-cli` 채널에 `web open|search|read|tabs` 동사를 추가해 사용.
  GUI가 없으면 `HeadlessWebFetcher`로 직접 가져오며 응답에 `via: gui|headless`.
- DOM/텍스트 분석은 `WebPageExtractor`(제목·설명·h1~h3·본문 문단·링크, `max_chars` 캡,
  `summary|links|find` 모드) 하나를 GUI·헤드리스 양쪽이 공유. 검색은 DuckDuckGo HTML
  파서. 페이지 텍스트는 `source: untrusted web content` 표식과 함께 데이터로 전달.

## 후속 수정 #2

**운영자 보고 (원문)**: "재생해달라고하면..디렉토리를 물음 하나밖에 없는데.. 그래서 특정경로를
안물어도 등록된 폴더를 먼저확인후 대응할수 있도록 등록된 디렉토리를 먼저 조회에 관련파일이
있나? 조회시도를 먼저 해봐야할것같아 가령 음악파일이면 음파일종류를 사전 검색하고, 텍스트나
문서인경우 관련 문서가 있는지 먼저 탐색한후 찾아들어가는 스텝을 이용해야할것같음... 로그파악해서 개선"

**진단** — 호스트 로그 21:22 세션. 후속 #1의 정지(`stop_media: closed Microsoft.Media.Player`)와
검색 첫 결과 열기(`top_page` 455자)는 동작. 남은 문제는 "음악 재생해줘" → `list_files`(경로
없음)로 루트 목록 `{roots:[{alias:"root"}]}`만 받고 **두 번째 걸음(루트 안 목록)을 밟지 않은 채**
"경로를 알려달라"고 되물은 것. "이문세 노래"도 같은 한 걸음에서 "찾을 수 없다"로 끝남. 모델이
폴더 안으로 들어가는 스텝을 스스로 밟지 않으므로, 탐색을 툴이 대신한다.

**수정**

- `find_files { kind: media|image|document|any, query }` 신설 — 등록된 폴더 **전체**를
  종류(`FileOpenPolicy` 분류)와 이름 단어로 한 번에 검색, 일치 단어 수 점수순.
  `FileToolCore.FindFiles`(순수) → `AllowedRootFileTools.FindFiles`(루트 병합, alias 경로) →
  `FileToolActor.Find` / `WearableToolbelt` / WPF 툴벨트 / 두 루프 / 카탈로그(GBNF·KnownTools·프롬프트).
- `list_files`(경로 없음)가 루트마다 파일 미리보기(30개)를 함께 돌려줌 — 루트가 하나면 첫
  호출에 노래 목록이 보인다.
- 프롬프트 의도 맵: 재생 → `find_files(kind=media, query=가수·제목)` → `open_file`;
  문서 요약 → `find_files(kind=document)` → `read_file`; **폴더나 경로를 되묻지 말 것**
  (여러 후보가 있고 요청이 특정하지 않을 때만 질문).
