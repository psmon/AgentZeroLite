# F-2 → F-3 → F-1 수정 적용

## 실행 요약

첫 전체 감사(`2026-09-24-07-42-first-full-audit.md`)의 권장 순서를 그대로 따라
세 건을 수정했다. 전부 `ZeroCommon` — 세 호스트가 동시에 이득을 본다.

각 수정마다 **먼저 대상 코드를 전부 읽고, 고치고, 그 발견을 붙드는 테스트를
추가**했다. 테스트 없는 수정은 다음 세션에 되돌아간다.

## 결과

```
dotnet test Project/ZeroCommon.Tests   →  통과 928 / 건너뜀 24 / 실패 0
```

### 도중에 나온 두 가지 (기록 가치 있음)

**1. 회귀 테스트가 먼저 틀렸다.** F-2 의 두 번째 테스트가 처음엔 실패했는데,
원인은 수정이 아니라 테스트였다 — 두 런이 세마포어 하나를 공유해 첫 release 가
*두 번째* 런을 끝냈다. 즉 실패하지 않았다면 **잘못된 이유로 통과**했을 테스트다.
런마다 게이트를 분리(`BlockingLoopFactory`)하고 그 사실을 테스트 주석에 남겼다.
F-5(정전 자체 결함)와 같은 종류의 실수이고, 같은 세션에 두 번 나왔다 —
**검증을 쓸 때는 그 검증이 실패할 수 있는지부터 확인한다**는 절차가 필요하다.

**2. I-10 신설 — 프롬프트 예산 위반 (Info, 미수정).** F-1 을 code-coach 의
`llm-prompt-conventions` R-2 에 맞추려고 측정하다 나왔다:

```
AgentToolGrammar.SystemPrompt = 18,089자 / 2,605단어 / 약 3,500토큰
R-2 상한 = "800토큰 훨씬 아래"          → 약 4.4배
기본 ContextSize = 2048                 → 프롬프트 혼자 초과
```

F-1 이 만든 문제가 아니다(추가 블록 60단어, R-2 의 블록 상한 이내). 그런데
**I-1…I-9 의 모든 규칙이 바로 그 프롬프트 안에 적혀 있다** — 컨텍스트가 넘치면
가장 먼저 밀려나는 것이 시스템 프롬프트다. 불변식으로 승격할 만하다.

축소는 시도하지 않았다: Mode 1/2/3 라우팅, 트리거 목록, verb 카탈로그가 전부
load-bearing 이고 R-2 자신이 `LlmProbe` bench 비교를 요구한다. 소유자는
code-coach, 감사관은 측정하고 보고할 뿐이다 (Rule 1).
